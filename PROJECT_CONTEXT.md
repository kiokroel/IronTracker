# IronTracker - Project Context & AI Rules

## Обзор проекта (Project Overview)
IronTracker — это бэкенд для платформы тяжелой атлетики и пауэрлифтинга на базе микросервисной архитектуры. Пользователи ведут дневники тренировок (жим лежа, приседания, становая тяга, бег), а система в реальном времени строит лидерборды по тоннажу и собирает глубокую аналитику.

## Технологический стек (Tech Stack)
- **Язык/Фреймворк:** Python 3.12+, FastAPI, Pydantic v2
- **Шлюз (API Gateway):** Caddy (или Nginx)
- **Базы данных:** PostgreSQL (реляционные данные), MongoDB (аналитика/Time Series)
- **Кэш/Лидерборды:** Redis (активное использование ZSET)
- **Брокеры сообщений:** Kafka (Fact events/События), RabbitMQ (Command events/Очередь задач)
- **Инфраструктура:** Docker, Docker Compose

## Архитектура и зоны ответственности (Microservices Architecture)

1. **Workout Service (FastAPI + PostgreSQL)**
   - **Ответственность:** CRUD тренировок, базовая валидация, аутентификация.
   - **Правила работы с БД:** Используется SQLAlchemy 2.0 (async). Общие параметры (ID, дата, юзер) лежат в жестких колонках. Специфичные метрики (повторения, вес для железа ИЛИ дистанция, пульс для кардио) ОБЯЗАТЕЛЬНО хранятся в колонке типа `JSONB`.
   - **События:** При сохранении тренировки сервис отправляет событие в Kafka. ОБЯЗАТЕЛЬНО использование паттерна **Transactional Outbox** (события сначала пишутся в таблицу `outbox` в PostgreSQL в одной транзакции с тренировкой, а затем фоновый процесс/воркер публикует их в Kafka).

2. **Leaderboard Service (FastAPI + Redis)**
   - **Ответственность:** Реалтайм-рейтинги пользователей.
   - **Правила:** Никаких долгих расчетов в памяти приложения. Все рейтинги (например, тоннаж за неделю) считаются исключительно силами Redis через структуры `Sorted Sets (ZSET)`. 

3. **Analytics Service (Async Worker + Kafka + MongoDB)**
   - **Ответственность:** Расчет макро-показателей, прогрессии нагрузок, графиков.
   - **Правила:** Фоновый сервис (чистый `asyncio` или `FastStream`). Асинхронно консьюмит топики Kafka. Сохраняет агрегированные данные в MongoDB. Для временных рядов (прогрессия 1RM по дням) желательно использовать Time Series коллекции MongoDB. FastAPI допускается только для эндпоинта проверки работоспособности (`/health`).

4. **Notification Service (Async Worker + RabbitMQ)**
   - **Ответственность:** Отправка email/push уведомлений (ачивки, пробитие плато).
   - **Правила:** Изолированный фоновый Consumer из очереди RabbitMQ (`aio-pika` или `FastStream`). Обеспечивает логику ретраев при падении сторонних провайдеров (Dead Letter Exchange).

## Строгие правила для ИИ-агента (AI Directives)
1. **Не смешивать брокеры:** Kafka используется ТОЛЬКО для потока данных и бизнес-событий (тренировка завершена). RabbitMQ используется ТОЛЬКО для адресных команд (отправь письмо). Не предлагай заменить одно на другое — это учебное требование проекта.
2. **Согласованность данных (Data Consistency):** Никогда не предлагай прямую запись (Dual Write) одновременно в БД и в Kafka. Всегда используй Transactional Outbox.
3. **Асинхронность:** Весь I/O код (БД, Redis, HTTP-запросы) должен быть строго асинхронным (async/await, asyncpg, motor для mongo, redis.asyncio; библиотека aioredis строго запрещена).
4. **Ответы:** Пиши лаконичный код. При генерации моделей Pydantic всегда указывай строгую типизацию. Не удаляй существующие комментарии из кода при его модификации.
5. **Управление задачами через Notion:** Все задачи берутся и отслеживаются строго через Notion (база данных задач/канбан-доска `IronTracker: Kanban Board` через Notion MCP). Перед началом работы задача переводится в статус `In progress`, создается отдельная ветка в Git по правилам Git Flow, а по завершении реализации и прохождения тестов статус обновляется на `Done`.
