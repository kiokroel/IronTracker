# IronTracker Agent Guidelines

## Ханес: IronTracker (`irontracker-plugin`)

**Цель:** Автоматизация полного цикла разработки, тестирования и архитектурного контроля микросервисов и пользовательского интерфейса IronTracker по мультиагентной схеме (Разработчик [Backend/Frontend] -> Тестировщик -> Критик).

**Триггер:** При любых запросах на разработку фич, создание/изменение API эндпоинтов, моделей, миграций БД, интерфейса React/TypeScript или аудит бэкенда/фронтенда IronTracker обязательно используй навык `iron-orchestrator`. Простые вопросы общего характера могут обрабатываться напрямую.

## Мониторинг активности и предотвращение зависаний (Liveness & Healthcheck)
- **Периодический контроль субагентов:** При запуске длительных задач субагентов оркестратор (`iron-orchestrator`) обязан периодически контролировать их жизнеспособность (проверять состояние через `manage_subagents` и активность логов `transcript.jsonl`).
- **Таймаут неактивности:** Если субагент находится в состоянии выполнения без новых действий или ответов дольше 3–5 минут (зависание стрима генерации/сетевой сбой API), оркестратор обязан:
  1. Проверить фактический прогресс и состояние модифицированных файлов (`git status`, `git diff`, артефакты в `_workspace/`).
  2. Послать контрольный запрос или принудительно завершить зависший процесс (`manage_subagents kill`).
  3. Восстановить контекст, зафиксировать промежуточный отчет и перезапустить этап или передать управление следующему агенту пайплайна.

## Инфраструктура: Изоляция через Docker (Zero Host Clutter)
- Вся инфраструктура микросервисов (PostgreSQL, Redis, MongoDB, Kafka, RabbitMQ) запускается ИСКЛЮЧИТЕЛЬНО в Docker-контейнерах через `docker compose up -d`.
- Категорически запрещено использовать локально установленные службы хоста, чтобы исключить засорение операционной системы и гарантировать воспроизводимость.

## Политика моделей субагентов (Model Tier Strategy)
- **`iron-tester` (Тестировщик):** запускается строго на модели уровня `flash` — для быстрого выполнения консольных проверок (`pytest`, `tsc`, `bandit`, `ruff`) и максимальной экономии квот.
- **`iron-critic` (Архитектурный цензор и ИБ):** запускается строго на флагманской модели `pro` — для глубокого смыслового анализа архитектуры, выявления IDOR, скрытых состояний гонки (race conditions) и аудита безопасности.
- **`iron-developer` / `iron-frontend` (Разработчик):** использует режим `inherit` (или `pro` при проектировании новой микросервисной архитектуры с нуля).
