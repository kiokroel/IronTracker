# Стратегия тестирования и QA

## Юнит- и Интеграционное тестирование
- Бизнес-логика, не зависящая от I/O (например, парсинг специфичных JSONB полей для приседаний или становой тяги), покрывается изолированными юнит-тестами. Обязательно использование pytest-asyncio и декоратора @pytest.mark.asyncio для тестирования асинхронных корутин.
- Модели SQLAlchemy и Pydantic должны проходить тесты на валидацию некорректных типов данных.
- Интеграционные тесты для API должны проверять эндпойнт целиком. Рекомендуется использовать Testcontainers для поднятия изолированных инстансов PostgreSQL и Redis перед прогоном тестов (для брокеров в юнит/компонентных тестах допускается использование асинхронных моков или Testcontainers).

## Тестирование контрактов и консистентности
- Проверка Transactional Outbox: тесты Workout Service должны валидировать, что при успешном коммите тренировки в БД, запись в таблицу outbox появляется гарантированно, а при откате (rollback) транзакции — не появляется.
- Формат сообщений: События, отправляемые в Kafka, и команды для RabbitMQ должны валидироваться через общие Pydantic схемы контрактов на сериализацию и десериализацию.

## Производительность и нагрузка
- Эндпоинты Leaderboard Service (опирающиеся на Redis ZSET) и Workout Service должны быть спроектированы с учетом возможности проведения нагрузочного тестирования.
- Ответы API должны быть оптимизированы для исключения узких мест в запросах к БД, чтобы при запуске скриптов Apache JMeter система выдерживала расчетную пропускную способность без деградации времени ответа.
