# Стратегия тестирования и QA

## 1. Пирамида тестирования и разделение ответственности
В монорепозитории IronTracker действует строгое разделение тестовых уровней и инструментов по стекам технологий:

1. **Backend Testing (`tests/`):**
   - Фреймворк: `pytest` с `pytest-asyncio` (`@pytest.mark.asyncio`).
   - Клиент: `httpx.AsyncClient` с `ASGITransport` для прямого async тестирования FastAPI приложений без подъема сетевого порта хоста.
   - Базы данных и брокеры: асинхронные моки (`AsyncMock`) или изолированные Testcontainers в Docker.
   - Область: валидация бизнес-логики сервисов, Pydantic-схем, SQLAlchemy моделей, контроллеров, репозиториев, Transactional Outbox и фоновых воркеров.

2. **Frontend Testing (`frontend/`):**
   - Фреймворк: Нативный `vitest` (`npm test` / `npx vitest run`).
   - Проверка типов: `tsc --noEmit` (`npm run lint`).
   - Область: математические и спортивные формулы 1RM (`fitness.ts`), утилиты дат и форматирования (`date.ts`), управление состоянием Zustand (`useAuthStore.ts`), хуки и изоляция UI-логики.
   - **Запрещено:** проверять клиентский TypeScript/React-код из Python-тестов.

3. **Инфраструктурные и контрактные тесты (`tests/`):**
   - Проверка контрактов брокеров сообщений (Kafka / RabbitMQ) на базе общего пакета `shared/contracts/`.
   - Проверка целостности спецификаций Caddy Gateway и конфигураций `docker-compose.yml`.

## 2. Категорический запрет антипаттерна «Тесты ради тестов» (Zero Vanity Testing)
Запрещено создавать фиктивные или поверхностные тесты для искусственного накручивания метрик покрытия:

- **Запрет текстового парсинга исходников через Python:** Категорически запрещено писать pytest-тесты, которые читают файлы фронтенда (`.ts`, `.tsx`, `package.json`), Markdown (`SKILL.md`, `AGENTS.md`) или конфигурации плагинов (`plugin.json`, `agent.json`) через `Path.read_text()` и проверяют наличие ключевых слов (`assert "interface User" in text`, `assert "React 18+" in text`).
- **Запрет дублирования компилятора и линтеров:** Тесты не должны проверять то, что гарантируется статическим анализом (`tsc --noEmit`, `mypy --strict`, `ruff check .`). Наличие экспортов, сигнатуры интерфейсов и синтаксис проверяются компилятором, а не модульными тестами.
- **Запрет тривиальных тестов без инвариантов:** Тест обязан проверять бизнес-логику, контракты данных, граничные условия, обработку ошибок или поведение при откатах транзакций. Тестирование тривиальных геттеров/сеттеров без логики запрещено.

## 3. Юнит- и Интеграционное тестирование Backend
- **Бизнес-логика и JSONB метрики:** Все вычисления (тоннаж, 1RM, темп бега) и валидация полиморфных схем `JSONB` обязаны покрываться изолированными тестами. Валидация Discriminated Unions Pydantic v2 проверяется на корректные и некорректные полезные нагрузки (HTTP 422).
- **Интеграционные тесты API:** Проверяют эндпоинты сквозным образом через `httpx.AsyncClient` с проверкой HTTP статус-кодов, схемы ответов и заголовков.

---

## 4. Тестирование контрактов и консистентности
- **Transactional Outbox:** Тесты `Workout Service` обязаны верифицировать атомарность:
  - При успешном коммите тренировки запись события в таблицу `outbox` создается строго в той же транзакции.
  - При ошибке или откате (`rollback`) транзакции запись в `outbox` гарантированно отсутствует.
  - Message Relay (`outbox processor`) корректно обновляет статусы `pending -> processed` и инкрементирует `retry_count` при сбоях брокера.
- **Схемы брокеров:** События Kafka и команды RabbitMQ сериализуются и десериализуются через централизованные Pydantic-схемы из `shared/contracts/`.

---

## 5. Тестирование безопасности и аудит уязвимостей
- **Статический анализ безопасности (SAST):** Обязательный запуск `bandit -r workout_service/ leaderboard_service/ analytics_service/ notification_service/ users_service/ shared/ tests/ -ll`. Критические (High) и средние (Medium) замечания должны равняться 0.
- **Аудит сторонних зависимостей:** Регулярный запуск `pip-audit` для предотвращения уязвимостей с известными CVE в Python-пакетах.
- **Тестирование разграничения прав (IDOR):** Тесты API обязаны проверять невозможность чтения, изменения или удаления чужих тренировок и ресурсов другими атлетами (HTTP 403 или HTTP 404).
- **Параметризация запросов:** Проверка экранирования и защиты от SQL-, NoSQL- и JSON-инъекций.

---

## 6. Чек-лист качества тестов (Quality Gate)
Перед сдачей задачи инженер обязан убедиться:
1. `pytest tests/` проходит на 100% без flaky-тестов.
2. `npm test` во `frontend/` проходит на 100% за секунды.
3. `tsc --noEmit` и `vite build` завершаются без ошибок.
4. В тестовом наборе отсутствуют строковые парсеры чужих исходных файлов.
