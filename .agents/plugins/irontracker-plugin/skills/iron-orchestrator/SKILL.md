# IronTracker Orchestrator

Оркестратор мультиагентного цикла разработки бэкенда IronTracker на базе Antigravity CLI. Координирует работу специализированных субагентов (Разработчик, Тестировщик, Критик) по строгому циклу: `Developer -> Tester -> Critic` с механизмом автоматических итераций до получения `VERDICT: APPROVED`.

## Режим выполнения: Субагенты (Последовательный пайплайн с циклом обратной связи)

## Состав команды субагентов

| Субагент (TypeName) | Роль | Зона ответственности | Основной артефакт |
|:---|:---|:---|:---|
| `iron-developer` | Ведущий разработчик | Код сервисов, моделей, роутеров, Outbox, Pydantic DTO, Secure Coding | `_workspace/01_developer_report.md` |
| `iron-tester` | QA & Инженер безопасности | Unit/интеграционные тесты, pytest, ruff, mypy, bandit, pip-audit, IDOR | `_workspace/02_tester_report.md` |
| `iron-critic` | Архитектурный цензор и аудитор ИБ | Аудит 01-architecture, 02-code-style, 03-testing, аудит бэкдоров/секретов | `_workspace/03_critic_report.md` |

## Воркфлоу оркестрации

### Phase 0: Проверка контекста (Поддержка повторных и частичных запусков)

Перед запуском проверь состояние рабочего пространства:

1. Проверь наличие директории `_workspace/`:
   - **`_workspace/` отсутствует** → Первичный запуск. Переходи к Phase 1.
   - **`_workspace/` существует И пользователь просит исправить/доработать/перепроверить** → Частичный перезапуск. Сохрани историю замечаний и перезапусти только необходимых субагентов (например, разработчика по замечаниям критика).
   - **`_workspace/` существует И пользователь передал абсолютно новую задачу** → Создание нового цикла. Перемести старый `_workspace/` в `_workspace_archive_{timestamp}/` и создай чистый `_workspace/`.

### Phase 1: Подготовка и инициализация

1. Проанализируй входную задачу:
   - Требуется ли создание нового эндпоинта (активируй навыки `endpoint-developer`)?
   - Требуется ли изменение схемы БД (активируй навыки `db-migrator`)?
   - Затронут ли Workout Service (критично наличие Transactional Outbox)?
2. Создай директорию `_workspace/` и поддиректорию `_workspace/00_input/`.
3. Сохрани структурированное описание задачи в `_workspace/00_input/task.md`.

### Phase 2: Фаза Разработчика (`iron-developer`)

Запусти субагента-разработчика через `invoke_subagent`:
- **TypeName**: `iron-developer`
- **Role**: `Lead Backend Developer`
- **Prompt**:
  ```
  Изучи задачу в _workspace/00_input/task.md.
  Если в _workspace/03_critic_report.md есть замечания предыдущей итерации, устрани их в первую очередь.
  Реализуй изменения строго по правилам IronTracker:
  - Python 3.12+, FastAPI, SQLAlchemy 2.0 (async).
  - from __future__ import annotations во всех моделях/схемах.
  - JSONB метрики валидируй строго через Pydantic v2 Discriminated Unions.
  - Запрещен Dual Write: в Workout Service события сохраняются в таблицу outbox в той же транзакции БД.
  - Только асинхронный I/O (asyncpg, motor, redis.asyncio, aiokafka, aio-pika).
  - Стандарты безопасности: запрет eval/exec/pickle/subprocess, отсутствие захардкоженных секретов (только .env/pydantic-settings), защита от инъекций и IDOR.
  Зафиксируй результаты своей работы в файле _workspace/01_developer_report.md.
  ```
Ожидай завершения работы разработчика.

### Phase 3: Фаза Тестировщика (`iron-tester`)

После получения отчета разработчика запусти субагента-тестировщика через `invoke_subagent`:
- **TypeName**: `iron-tester`
- **Role**: `QA Automation & Security Engineer`
- **Prompt**:
  ```
  Ознакомься с отчетом разработчика в _workspace/01_developer_report.md и измененным кодом.
  Выполни полный цикл проверок качества и безопасности:
  1. Запусти линтинг: ruff check . && ruff format --check .
  2. Запусти проверку типов: mypy --strict .
  3. Запусти SAST-анализ безопасности: bandit -r workout_service/ leaderboard_service/ analytics_service/ notification_service/ shared/ tests/ -ll
  4. Запусти аудит уязвимостей зависимостей: pip-audit
  5. Напиши/дополни тесты на pytest с httpx.AsyncClient и @pytest.mark.asyncio.
  6. Проверь атомарность Transactional Outbox:
     - При коммите создается запись outbox со статусом 'pending';
     - При ошибке/откате транзакции запись outbox отсутствует.
  7. Проверь валидацию JSONB: некорректные данные вызывают 422 Unprocessable Entity.
  8. Проверь защищенность эндпоинтов (IDOR, корректность обработки чужих ресурсов).
  Зафиксируй отчет в _workspace/02_tester_report.md со статусом (PASS/FAIL) и полными логами/стектрейсами/отчетами безопасности.
  ```
Ожидай завершения тестирования.

### Phase 4: Фаза Критика (`iron-critic`)

Запусти субагента-критика через `invoke_subagent`:
- **TypeName**: `iron-critic`
- **Role**: `Principal Architecture & Security Auditor`
- **Prompt**:
  ```
  Проведи строгий архитектурный аудит и аудит безопасности изменений на основе:
  - Кодовой базы проекта;
  - Отчета разработчика _workspace/01_developer_report.md;
  - Отчета тестировщика _workspace/02_tester_report.md.
  Проверь соблюдение:
  1. Отсутствие Dual Write (Transactional Outbox).
  2. Валидацию JSONB метрик через Discriminated Unions в Pydantic v2.
  3. Изоляцию брокеров (Kafka - факты, RabbitMQ - команды).
  4. Строгий асинхронный I/O (нет aioredis, нет блокирующих вызовов).
  5. Безопасность и отсутствие бэкдоров: запрет eval/exec/pickle/subprocess, отсутствие хардкода секретов/токенов, отсутствие скрытых debug-ручек, чистые отчеты bandit и pip-audit.
  6. from __future__ import annotations и чистоту типизации.
  Вынеси однозначный вердикт в _workspace/03_critic_report.md:
  Либо VERDICT: APPROVED, либо VERDICT: REJECTED с нумерованным списком правок (с категорией [Architecture / Security / Bug]).
  ```
Ожидай вердикта критика.

### Phase 5: Оценка вердикта и цикл обратной связи

Прочитай `_workspace/03_critic_report.md`:
- **Если вердикт `VERDICT: APPROVED` И тесты зеленые (PASS):**
  Переходи к Phase 6 (Финализация).
- **Если вердикт `VERDICT: REJECTED` ИЛИ тесты красные (FAIL):**
  - Проверь счетчик итераций (максимум 3 цикла).
  - Если лимит не исчерпан: повторно запусти Phase 2 (`iron-developer`), передав отчет критика `_workspace/03_critic_report.md` как обязательное ТЗ на доработку.
  - Если лимит исчерпан: сформируй сводный отчет для пользователя с указанием неразрешенных архитектурных конфликтов.

### Phase 6: Автоматическая финализация (Commit, Push & Pull Request)

Как только изменения утверждены (получен вердикт `VERDICT: APPROVED` от архитектурного критика и получено подтверждение):

1. **Автоматическое создание коммита:**
   - Добавить все измененные файлы в индекс:
     ```powershell
     git add .
     ```
   - Сформировать атомарный коммит по спецификации Conventional Commits (`<type>(<scope>): <subject>`):
     ```powershell
     git commit -m "<type>(<scope>): <subject>"
     ```

2. **Автоматический пуш ветки в удаленный репозиторий:**
   - Отправить изменения в удаленную ветку:
     ```powershell
     git push -u origin <current-branch>
     ```

3. **Автоматическое создание Pull Request с подробным описанием:**
   - Сформировать подробное описание PR на основе артефактов `_workspace/` (`01_developer_report.md`, `02_tester_report.md`, `03_critic_report.md`):
     - **## Обзор задачи и изменений (Summary):** краткая суть фичи/исправления, затронутые микросервисы.
     - **## Архитектурный аудит и безопасность (Architecture & Security Compliance):** вердикт `VERDICT: APPROVED`, подтверждение соблюдения Transactional Outbox (отсутствие Dual Write), строгой типизации JSONB, разделения брокеров, асинхронного I/O и отсутствие бэкдоров/утечек секретов.
     - **## Результаты тестирования и аудита (QA & Security Report):** статус `pytest`, `ruff check`, `mypy --strict`, `bandit` (0 issues), `pip-audit` (0 CVEs), тесты Outbox rollback/commit, тесты IDOR.
     - **## Чек-лист верификации (Checklist):** пройденные проверки стандартов качества и безопасности IronTracker.
   - Вызвать инструмент GitHub MCP `create_pull_request` (или CLI `gh pr create`):
     - `owner`: владелец репозитория (например, `kiokroel`);
     - `repo`: `IronTracker`;
     - `title`: заголовок PR по Conventional Commits;
     - `head`: текущая ветка;
     - `base`: `main`;
     - `body`: сгенерированное описание PR.

4. **Закрытие задачи:**
   - Если задача велась в Notion — обновить статус карточки в `Done`.
   - Вывести пользователю итоговый отчет и прямую ссылку на созданный Pull Request.

```
[Оркестратор]
    │
    ├── 1. Запись ТЗ ──────────→ _workspace/00_input/task.md
    │
    ├── 2. invoke(developer) ──→ _workspace/01_developer_report.md
    │                                    │
    │                                    ↓ (Изучение кода и отчета)
    ├── 3. invoke(tester) ─────→ _workspace/02_tester_report.md
    │                                    │
    │                                    ↓ (Аудит тестов и решений)
    ├── 4. invoke(critic) ─────→ _workspace/03_critic_report.md
    │                                    │
    ├── 5. Оценка вердикта ──────────────┘
    │       ├── REJECTED ──────→ Возврат к Developer (с замечаниями)
    │       └── APPROVED ──────→ Запрос подтверждения у пользователя → Финализация
```

## Обработка ошибок и непредвиденных ситуаций

| Ситуация | Стратегия реагирования |
|:---|:---|
| Ошибка выполнения субагента | 1 повторный вызов с уточнением контекста ошибки. При повторном падении — пауза и запрос к пользователю. |
| Зависание субагента (> 3-5 мин без действий / сбой API стрима) | Liveness check: проверить реальный прогресс файлов (git status/diff), при необходимости завершить процесс (manage_subagents kill), зафиксировать артефакты и передать эстафету следующему шагу или перезапустить. |
| Падение тестов pytest | Возврат отчета тестировщика разработчику для немедленного исправления логики. |
| Исчерпание 3 итераций цикла | Формирование детального отчета со списком разногласий и запрос ручного вмешательства пользователя. |
| Отсутствие файлов в _workspace | Автоматическое восстановление структуры и перезапуск соответствующей фазы. |

## Тестовые сценарии оркестрации

### Сценарий 1: Успешный цикл (Happy Path)
1. Пользователь запрашивает реализацию эндпоинта логирования подходов в Workout Service.
2. Оркестратор фиксирует требования в `_workspace/00_input/task.md`.
3. `iron-developer` реализует DTO, модели, outbox-репозиторий и роутер.
4. `iron-tester` пишет интеграционные тесты, подтверждает прохождение ruff, mypy и pytest.
5. `iron-critic` проверяет отсутствие Dual Write, валидацию JSONB и выдает `VERDICT: APPROVED`.
6. Оркестратор запрашивает у пользователя разрешение на коммит и фиксирует изменения.

### Сценарий 2: Возврат на доработку (Rejection & Retry Loop)
1. `iron-developer` случайно использует прямую публикацию в Kafka вместо записи в Outbox.
2. `iron-tester` прогоняет тесты, они успешны по функционалу, но Outbox не проверялся.
3. `iron-critic` обнаруживает Dual Write и выдает `VERDICT: REJECTED` с указанием строки нарушения.
4. Оркестратор возвращает задачу `iron-developer` с отчетом критика.
5. `iron-developer` переписывает сохранение на Transactional Outbox в рамках единой транзакции БД.
6. `iron-tester` добавляет тест на проверку записи в Outbox.
7. `iron-critic` проводит повторный аудит и выдает `VERDICT: APPROVED`.
